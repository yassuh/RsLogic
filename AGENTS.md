# RsLogic Agent Notes

These notes are for AI agents and automation working in this repository without
the prior chat history.

## Hard Rules

- All RsLogic jobs must be submitted through the management API and executed by
  `rslogic-agent` spawning `rslogic-worker`.
- Do not start RealityScan, Docker, or Podman job containers directly as the
  execution path for a new job. Direct remote commands are acceptable only for
  inspection, diagnostics, screenshots, log tails, or cleanup the user explicitly
  requests.
- Do not casually restart the active agent, worker, server, or RealityScan
  container while a job is running. Check the active process/container state
  first.
- Client machines must not store AWS credentials. Imagery should come from
  CloudFront signed URLs generated by the management server.
- Studio DB is legacy. v2 uses Studio API image asset truth.

## Project Shape

RsLogic v2 is a Rust-first client orchestration and RealityScan pipeline system.
The old Python implementation is preserved under `deprecated/v1-python/` and
should be treated as historical reference unless compatibility work is requested.

Workspace crates:

- `crates/rslogic-protocol`: shared protocol types for enrollment, auth, jobs,
  telemetry, WebSocket commands/events, artifacts, and RealityScan stages.
- `crates/rslogic-server`: local management API for enrollment, WebSocket
  control, job assignment, Studio API image resolution, CloudFront signed
  manifests, job events, and artifact records.
- `crates/rslogic-agent`: long-running client daemon on `yassuh-1`; it enrolls,
  authenticates, opens an outbound WebSocket, sends telemetry, and spawns the
  worker for assigned jobs.
- `crates/rslogic-worker`: per-job pipeline executor; it restores/downloads
  imagery, verifies inputs, runs RealityScan through Docker/Podman, collects
  outputs, and emits structured job events.
- `crates/rslogic-realityscan`: thin container/CLI adapter for RealityScan.
- `apps/dashboard`: Vite + React + shadcn-style local dashboard.

## Job Progress

The dashboard separates overall job progress from current stage progress. Do
not collapse those concepts into a fallback percentage.

RealityScan does not expose a complete percentage for every CLI step. When a
stage percentage is unknown, show an indeterminate stage animation and continue
capturing command lines, phase heartbeats, and parsed status messages.

Useful API routes:

- `GET /api/admin/clients`
- `GET /api/admin/jobs`
- `GET /api/admin/job-events?job_id={job_id}&limit=200`
- `GET /api/admin/events`
- `POST /api/admin/clients/{client_id}/jobs`
- `POST /api/admin/jobs/build`

Durable worker events are written under each job:

```text
logs/job-events.jsonl
logs/realityscan-*.stdout.log
logs/realityscan-*.stderr.log
state.json
```

## RealityScan Notes

- Current seaFORTH test jobs use DJI M4E imagery.
- Studio API camera intrinsics endpoint used during planning:
  `GET /api/v1/camera-intrinsics/DJI%20M4E`.
- Known DJI M4E distortion values:
  `radial_1=-0.036013`, `radial_2=-0.004848`, `radial_3=0.000481`.
- RealityScan CLI stdout provides useful progress-like messages for some stages,
  especially command execution, feature detection counts, and completion lines.
  Preserve and parse those where possible.

## Local Development Commands

Prefer Docker for host-independent builds/tests:

```powershell
docker run --rm -v "${PWD}:/work" -w /work rust:latest cargo test -p rslogic-agent
docker run --rm -v "${PWD}:/work" -w /work rust:latest cargo test -p rslogic-worker
docker run --rm -v "${PWD}:/work" -w /work rust:latest cargo test -p rslogic-server
docker run --rm -v "${PWD}:/work" -v rslogic_dashboard_node_modules:/work/apps/dashboard/node_modules -w /work/apps/dashboard node:24-bookworm bash -lc "npm run build"
```

Static Linux client binaries for manual NixOS testing:

```powershell
docker run --rm -v "${PWD}:/work" -v rslogic-cargo-cache:/usr/local/cargo/registry -w /work -e CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS="-C target-feature=+crt-static" rust:latest cargo build --release --target x86_64-unknown-linux-gnu -p rslogic-agent -p rslogic-worker
```

Manual copy locations, if needed after a job is not active:

```powershell
scp target\x86_64-unknown-linux-gnu\release\rslogic-agent yassuh-1:/tmp/rslogic-v2-jobs/rslogic-agent.new
scp target\x86_64-unknown-linux-gnu\release\rslogic-worker yassuh-1:/mnt/storage/rslogic-v2-jobs/rslogic-worker.new
```

## Deployment Direction

Target state:

1. This repo exposes a Nix flake package named `rslogic-client` containing
   `rslogic-agent` and `rslogic-worker`.
2. `yassuh-nixos` consumes this repo as a flake input.
3. Updating a client is done through `nix flake lock --update-input rslogic`
   and `sudo nixos-rebuild switch --flake .#yassuh-1`.
4. Automatic deployment should remain gated by review until the management
   server is stable.
